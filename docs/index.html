the build

One console, five primitives, all invariants tested

Roles (server-enforced)

  • DEVELOPER: create, edit, submit drafts
  • RELEASE_APPROVER: approve, reject, apply, roll back
  • AUDITOR: read everything, mutate nothing

State machine

DRAFT -> PENDING_APPROVAL -> APPROVED -> APPLIED -> ROLLED_BACK
                        \-> REJECTED

Guarantees

  • Requester can never approve their own change
  • Every transition appends an audit event in the same DB transaction
  • Optimistic version check rejects stale or duplicate actions
  • Fake-provider failure leaves state untouched, no false audit

Architecture

  • Next.js App Router + Prisma + PostgreSQL, all in Docker Compose
  • FakeFlagProvider behind a FeatureFlagProvider interface
  • Multi-stage image, non-root runtime, healthcheck-gated startup

      limits and next step

      What this does not prove, and the gate before any migration

      Not built, on purpose

      • No real flag provider (no idempotency, reconciliation, or outbox)
      • No SSO/OIDC; seeded credential accounts only
      • No DLP-equivalent governance layer
      • No durable, database-enforced audit retention
      • No deployment; local Docker Compose only

      Proposed 90-day controlled pilot

      • Run this control plane against virtual flags with real workflows
      • Classify flags; payment, KYC, access, risk flags stay excluded
      • Build the provider adapter for one real, low-risk flag system
      • Devin delivers each increment through the same PR + review loop

      The gate

      • Security review of authz, audit, and provider path
      • Only then: decide whether any Power Apps tool migrates
